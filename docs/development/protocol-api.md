# Protocol integration API

Package `dev.mx3.nomessages.core.protocol`. All calls synchronous on the vault's serialized IO dispatcher. Opaque exports contain secret material and MUST ONLY persist inside SQLCipher. Official libsignal 0.102.2 currently mandates PQXDH: this is an explicit deviation from SPEC classical X3DH, never advertised as classical X3DH.

- `PairingIdentity.create(crypto: Crypto): PairingIdentity`; `export(): ByteArray`; `PairingIdentity.restore(blob): PairingIdentity`; `publicKey: ByteArray` Ed25519; `id: String` lowercase public-key hex; implements AutoCloseable. Contains Ed25519 keypair and `sessions: SignalSessions`. `restoreInPlace(blob)` rolls back complete identity/session state preserving object identity (rejects changed Ed25519 ID). `signingSeed(): ByteArray` returns copied libsodium Ed25519 seed32 for MLS, caller wipes immediately.
- `PairingEngine(crypto, identity, onion: String, doorbellKey: ByteArray, now: () -> Long = epochSeconds, consumed: MutableSet<String> = mutableSetOf())`. Persist consumed set with identity transaction; all tokens used/expired within TTL cannot be accepted again. `consumed` values are hex SHA256 QR hashes. `doorbellKey` is 32 non-zero bytes — see "Doorbell fields" below.
- `createOffer(): String` creates a `nomessages:2:` protobuf QR and puts it on screen. **Display and validity are separate**: every offer already emitted stays able to receive a response and answer a `BundleRequest` for its own full 300 s, counted from its own `created` and regardless of whether it is still displayed. Because an offer lives 300 s while the screen rotates every 120 s, `ceil(300 / 120) = MAX_LIVE_OFFERS = 3` offers are concurrently valid at the peak; the cap is derived, never truncates normal operation, and exists to bound the set if the clock or the caller misbehaves. An entry ages out on its own schedule, never by being displaced by a newer one. A pending exchange, by contrast, is burned, because asking for a new QR mid-exchange is an explicit restart. UI MUST use error correction L. The payload measures 405 bytes / QR version 13 (offer), 448 / version 14 (response) and 317 / version 11 (confirmation), against the hard 8192-byte ceiling enforced by `Wire.kt::fromQr`.
- `receive(qr: String): PairingProgress` parses bounded offer/response kind and routes safely; an initial incoming offer cancels the outgoing local offer.
- `respond(offerQr: String): PairingProgress` consumes offer, produces `responseQr`, `sas`, `peerId`, `peerOnion`, `handle`, `expiresAt` in epoch seconds, `peerBundleNonce` and `peerBundleReady`. The deadline is now `PENDING_TTL_SECONDS` (300) after the **oldest** offer; UI must not restart it on each step.
- `processResponse(responseQr: String): PairingProgress` consumes a response for **any still-live local offer** — the whole `standingOffers()` set, up to `MAX_LIVE_OFFERS` of them — matched by the offer digest in `reply`; same SAS and deadline as the responder; `responseQr` is null until the local user confirms the SAS. The incoming response is bounded by `PENDING_TTL_SECONDS` (300), **not** by the 120-second QR-reading TTL: a response is not a standing invitation, it is not regenerated, and the peer's screen keeps it up — and shows that clock — for the whole exchange window. Enforcing 120 s here made the engine contradict the visible countdown and failed an ordinary live pairing (T4.16 run5). `standingOffers()` is the single shared definition of "an offer of mine that is still live", used by both this method and `bundleFor`.
- `acceptPeerBundle(handle: String, encoded: ByteArray): PairingProgress` accepts the peer's PQXDH bundle fetched over Tor. Requires `SHA-256(encoded) == peerOffer.bundleHash`, that the exchange has no bundle yet, and that the blob decodes as a valid signed `SignalBundle`. **Any failure cancels the exchange** and throws; there is no half-verified state. Returns the progress with `peerBundleReady = true`.
- `bundleFor(nonce: ByteArray): ByteArray?` returns the encoded bundle behind one of **this device's own** offers, or null. Answers only for a 16-byte nonce this device itself minted (any of the up-to-`MAX_LIVE_OFFERS` still-valid emitted offers, plus the one inside the pending exchange), only inside that offer's own 300 s window, and **exactly once**. Staging an exchange discards the key material of every other emitted offer, so an offer that can no longer lead anywhere is never answered for. Unknown, stale and already-consumed nonces return null and must be answered with silence, never an error.
- `confirm(handle: String, matches: Boolean): String` returns signed confirmation QR `nomessages-confirm:2:` after user explicitly compared six digit SAS. `matches=false` aborts and throws.
- `finish(handle: String, peerConfirmationQr: String): PairedContact` requires BOTH local and peer confirmation **and the peer bundle**, returns `peerId`, `publicKey`, `onion`, `pairedAt`, `evidence: ByteArray`, `doorbellKey`, `doorbellToken`. Pins Ed25519-to-Signal identity and establishes the official Signal session **from the bundle fetched over Tor**. Persist contact, evidence, consumed, identity export together before success. Confirmation QR must be exchanged in person or over authenticated Signal; never send plaintext From metadata over Tor.
- `cancel()` burns pending offers, the superseded offer and pending exchange material.

### QR format 2 and the Tor bundle fetch (2026-09-17, T4.16)

The offer carries `bundleHash = SHA-256(SignalBundle.encode())` instead of the ~1832-byte bundle. Format 1 measured ~2950 bytes — QR version 40, 177 modules per side — which the user's Galaxy Note10+ camera could not read even filling a whole monitor; 1569 of those bytes were the mandatory Kyber-1024 public key.

Ten signed fields, `PairingEngine.OFFER_FIELD_KINDS = "ibbibbbbbb"`: `version(1) | ed(32) | onion(62) | created(~5 varint) | nonce(16) | bundleHash(32) | doorbellKey(32) | doorbellToken(32) | reply(0|32) | signature(64)` = 294 bytes (offer) / 326 (response). `signal`, `ephemeral` and the `bundle` blob of format 1 are gone: `bundleHash` covers the whole bundle, identity and one-time prekey included, so the substitution format 1 blocked by repeating those as signed outer fields is blocked here by one hash comparison. CBOR domain separators are `nomessages-offer-v2` and `nomessages-transcript-v2`. Format 1 QRs are rejected at the prefix **and** at the body's version field.

`SignalBundle` is wire version 3 and **self-contained** (`identity` and `pre` are inside the blob); `decode(bytes)` no longer takes them as arguments. `MAX_ENCODED_BYTES = 4096`; the real encoding is ~1832 bytes.

Fetch flow — **whoever just read a QR fetches from whoever showed it**: the QR reader connects to the onion the QR names, sends `BundleRequest(peerNonce)` and receives `BundleResponse(nonce, bundle)`. For the initial offer that is reader → shower; for the response QR, the original shower fetches from the responder. Both sides need Tor `READY`; if not, wait up to the deadline with UI feedback rather than failing immediately. `MessagingEngine.fetchPeerBundle(onion, nonce, timeoutMillis)` performs it and **must not be called with the engine mutex held** — the peer is running the mirror-image fetch against this device at the same time and answering it needs that same mutex.

Three deadlines on two clocks. `OFFER_TTL_SECONDS = 120` bounds how stale a **standing invitation** (an offer QR, empty `reply`) may be when scanned — that is the QR which regenerates itself. `PENDING_TTL_SECONDS = 300` is the **acquisition** budget, counted from each offer's own `created`: how long that offer stays answerable, covering both matching a response QR against it and answering a `BundleRequest` for it. `CONFIRMATION_TTL_SECONDS = 240` is the **confirmation** budget, counted from the moment `stage()` runs: the Tor bundle fetch (started by the runtime *after* staging, so it lives in this budget), the spoken SAS, the alias and both confirmation QRs.

**The original "300 s covers search + SAS + confirmation" framing no longer holds.** Total wall-clock time from first offer to a completed pairing may now exceed 300 s — up to ~300 s of acquisition plus 240 s of confirmation. This is deliberate and came from live measurement (T4.16 run6): with two QR rotations spent acquiring, the old offer-anchored deadline left 4–35 s for the entire human phase, and both live attempts were accepted by the protocol and then timed out. 240 s is derived from what actually happens post-staging (~103 s fetch allowing one failed attempt, ~30 s spoken SAS, ~20 s alias, ~60 s for two confirmation QRs ≈ 215 s, plus ~10 % headroom).

Each device counts confirmation from **its own** staging, so the two deadlines differ by the relay delay between them. In person that is seconds and the shared window is essentially the whole budget. A confirmation-phase timeout raises the same specific `"Pairing expired"` the UI maps to `pairing_timed_out`. `confirm`, `acceptPeerBundle` and `finish` are gated solely by `get(handle)`, which now enforces the confirmation deadline, and were never exposed to the which-offer-is-current question: an offer is superseded, an exchange is not, there is at most one pending exchange, and the confirmation QR carries the full `PairStatement` binding it to that exchange. A circuit to a freshly published onion routinely costs 5–40 s, which format 1 never had to spend.

### Doorbell fields — reserved for T4.17, no behaviour implemented

`doorbellKey` (32 bytes) is the Ed25519 identity key of a second, dedicated v3 onion derived from its own vault seed (`meta.doorbell_seed`), deliberately distinct from `onion_seed` so the two addresses are unlinkable. `doorbellToken` (32 bytes) is minted fresh per offer, like the nonce, so only that exchange's peer ever learns it. Both are inside the canonical signed bytes and therefore inside the SAS transcript — there is no separate hashing or signing path. `PairedContact` returns the peer's pair; the runtime stores them in `contacts.doorbell_onion`/`doorbell_token` (vault schema v3). Nothing reads them yet: no service listens, no notification exists. Design note: `doorbell-design.md`.

The field carries the **key**, not the 62-character address: a v3 address is `base32(pubkey32 || checksum2 || version1) + ".onion"`, of which only the key is not derivable, and with the textual address the response QR measured version 15 — over the version-14 budget. `OnionAddress.address()`/`publicKey()` convert between the two.

After a successful local `finish`, the UI retains its own signed confirmation QR until explicit Done/back so the other phone can complete the sequential scan. Completed UI state does not accept another finish or confirmation.
- `SignalSessions.encrypt(peerId: String, plaintext: ByteArray): ByteArray`; `decrypt(peerId: String, ciphertext: ByteArray): ByteArray`; `export(): ByteArray`; `SignalSessions.restore(blob): SignalSessions`; `close()`. Ciphertext carries only type+libsignal payload. `peerIdentity(peerId): ByteArray` returns pinned serialized Signal public identity. Each mutation rolls back on exception using a lazy per-entry undo journal; failed untouched candidate trials never clone the whole store. Root snapshots/restores if SQL transaction commit fails; save complete identity export alongside ciphertext/outbox in same SQL transaction. Both peers establish sessions; upstream libsignal handles simultaneous initiation.
- `SignalSessions.decryptCandidates(peerIds: Collection<String>, ciphertext: ByteArray, maxRegularTrials: Int = 1024): DecryptedSignal?` parses the native message once, filters prekey sender against pinned identity, and authenticates candidates with per-entry rollback; result fields `peerId`, `plaintext`. Maximum 1024 candidates. `maxRegularTrials` caps only regular ratchet trials; all prekey candidates still receive the cheap pinned-key filter. Runtime can rotate candidate order after a budget-exhausted null result so later contacts remain reachable on retry. Unknown-stream regular ciphertext still requires trials; runtime must bound unknown-stream bytes/rate and use an authenticated small reconnect probe before large payloads. `validateCiphertext(ciphertext)` performs parse-only validation when needed separately; do not redundantly call before `decryptCandidates`.
- `FrameCodec.encode(ciphertext: ByteArray): List<ByteArray>` emits length-prefixed padded frames (buckets256/1024/4096/16384, total max16MiB). `FrameCodec.read(input: InputStream): ByteArray?` reads ONE complete frame, returns null only on clean EOF. `FrameAssembler().accept(frame: ByteArray): ByteArray?` takes full encoded frame, returns ciphertext on final sequential chunk. Assembler belongs to ONE per-peer stream, never global. No sender identity field.

Package `dev.mx3.nomessages.core.groups`: `CliquePolicy(crypto).missingPairs(members: Collection<String>, evidence: Collection<ByteArray>): List<MissingPair>` validates bilateral signed pairing evidence and returns sorted missing pairs; `MissingPair(first: String, second: String)`. `requireClique` rejects missing pairs. Membership3..100, lowercase Ed25519 hex IDs, duplicate members rejected. One member claiming an edge is insufficient.

Public proof decoding for app gossip: `PairEvidence.decode(bytes)` is bounded to512bytes; `statement.first`, `statement.second`, `statement.transcript`, `statement.pairedAt`; `valid(crypto)` requires both Ed25519 signatures. Parsing alone MUST NOT grant trust. `PairStatement`/`PairEvidence` constructors are data containers, not validation shortcuts.
