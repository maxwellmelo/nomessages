# Pairing, libsignal, framing and clique policy

Implementation owns core `protocol/*`, `groups/*`, `main/proto/pairing.proto` and `ProtocolTest.kt`. Integration API is in `protocol-api.md`.

## Implemented

- Strict bounded protobuf 3 QR offers, canonical field order with duplicate/unknown-field and noncanonical-varint rejection; canonical unpadded base64url prefix. Ed25519 signature uses RFC8949 deterministic CBOR array with a domain separator and binds version, Ed25519 identity, serialized Signal identity, fresh one-time X25519 prekey, onion, timestamp, 16-byte nonce, complete PQXDH bundle and response-to-offer digest. TTL is strictly 120 seconds; future offers rejected. Runtime persists consumed QR hashes with identity/contact transactions.
- Both participants hash the ordered original offer and response, obtaining the identical six-digit SAS. Local explicit SAS approval signs the bilateral pairing statement; a separate confirmation QR conveys this signature. Finalization requires both confirmations over exactly the same statement. Mismatch burns pending key material; no peer contact/session is finalized from a unilateral third-party claim.
- Official `org.signal:libsignal-client:0.102.2` Java API and native implementation, no clone. Vault-owned Ed25519 identity pins each peer's libsignal identity, disallowing unknown peers and identity substitution. Signal records are serialized blobs in an in-memory store, with native deserialization returning fresh objects to preserve transactional semantics. Encryption/decryption journals only touched entries and rolls back on exception; untouched candidate trials do not copy the full store. Runtime must atomically persist the full identity export together with message/outbox state and restore the in-memory snapshot if SQL commit fails.
- Fresh one-time EC and Kyber prekeys for each QR. No account service, prekey server, mailbox, network call or plaintext sender field. Both peers establish their own sessions; official libsignal resolves simultaneous initiation.
- Bilateral Ed25519 evidence forms clique edges; complete group policy for 3–100 members, deterministic sorted missing pairs, duplicate-member/invalid-proof rejection. No sender-key or pairwise-fanout substitute for MLS.
- Ciphertext transport chunking with bounded 16 MiB total, strictly sequential fragments and exact padding buckets of 256/1024/4096/16384 bytes. Length-prefixed reader handles partial stream reads and distinguishes clean EOF from truncation. Assembler is scoped per peer stream. Fragment metadata is visible and untrusted; only successfully authenticated libsignal plaintext may be used.

## Explicit specification deviations and limits

1. **PQXDH is mandatory in maintained official libsignal.** Official Maven metadata only carries 0.86.6 onward; both 0.86.6 and 0.102.2 source `PreKeyBundle` require a Kyber key and signature, and classical-only overloads are absent. Root approved the explicit supported-library deviation: PQXDH plus maintained Signal ratchets instead of claiming classical X3DH. Upstream 0.102.2 also evolves ratchets beyond the historical classical baseline. No homegrown downgrade was added. Sources: [official artifact repository](https://build-artifacts.signal.org/libraries/maven/org/signal/libsignal-client/maven-metadata.xml), [pinned official sources](https://build-artifacts.signal.org/libraries/maven/org/signal/libsignal-client/0.102.2/libsignal-client-0.102.2-sources.jar).
2. **Pairing QR requires error correction L.** Mandatory Kyber1024 adds 1569 serialized public-key bytes. The bundle omits identity/prekey duplication (already in signed outer fields) so one base64url offer/response fits QR40-L's 2953-byte ceiling. QR version 40 has 177 modules before the quiet zone; rendered module size and camera/device scan ergonomics remain a physical-device gate.
3. **Immediate native-memory erasure is not guaranteed by upstream Java wrappers.** Stored secret byte arrays are wiped on close/rollback, but libsignal `SimpleOwner` wrappers rely on finalizers and expose no deterministic close method. No unsafe manual handle destruction is used. A release must not claim all native ratchet allocations are synchronously zeroized on lock; dedicated crypto process termination is one possible future mitigation. JVM temporary copies also have ordinary managed-memory limitations.
4. In-progress pairing is intentionally cancelled on lock/restart. Root persists consumed hashes but should not present contacts as paired until `finish` and the enclosing SQL transaction commit. Confirmation can be exchanged by QR entirely offline. Handshake/user clock synchronization and device-camera scan still require real-device testing.
5. Evidence authenticates that both identities signed a pairing statement; it cannot prove physical proximity against two colluding participants. The local explicit SAS ceremony is the security boundary.

## Validation

The protocol cases passed in the centralized core JVM gate (62 passed, zero failures; two unrelated conditional cleanup cases ran separately). Test cases include actual native libsignal exchange/serialized restore, ciphertext replay/tamper/rollback, SAS agreement, QR TTL/replay/signature/oversize/duplicate-field/bundle-substitution, persistent replay set, bilateral confirmation, trust substitution, graph forgery/limits/determinism and frame partial reads/truncation/reordering. Evidence is in `core/build/test-results/test/` and `build-logs/core-app-jdk21-sdk36.log`.

The suite additionally contains an official-libsignal X25519 known-answer test using both participants from [RFC 7748 §6.1](https://www.rfc-editor.org/rfc/rfc7748.html#section-6.1): it checks both derived public keys and both shared-secret computations. The pinned API is `ECPrivateKey.calculateAgreement(ECPublicKey)`; no custom DH implementation or obsolete `Curve` adapter is used. A deterministic 171-case malformed-QR corpus covers bit mutations, truncation, nonterminating/oversized varints, duplicate fields, invalid base64/prefixes and over-limit input, asserting rejection, unchanged receiver state, and subsequent valid-input recovery. This is bounded regression coverage, not a claim of exhaustive fuzzing. Both additions passed in the centralized JVM run.

## Read-only threat collector verification

Additional owned deliverables: `scripts/threat-gates.sh`, `docs/release-checklist.md`, and `docs/security-model.md`. Bash syntax, help and invalid-argument checks passed. A temporary fake-adb fixture exercised marker-absent, marker-detected and unavailable-dump cases; verified explicit serial propagation, refused mutation commands, no extraction of a traversal-named archive entry and no marker contents in stdout/stderr. Fixture outcomes are script behavior checks, **not device security passes**. No real adb/device was used. All substantive device release gates remain NOT_RUN pending real evidence.

## Independent static integration review

Reviewed the native Tor/MLS bridges and runtime group control paths without changing their owner files. The review identified a Tor generation check/removal race, growth of the Java Tor argument buffer after copying the onion seed, and a missing immediate KeyPackage expiry check at Welcome acceptance. The owners report fixes for all three; executable regression evidence remains part of the shared build. The native MLS process path now parses wire messages before state deserialization to reduce malformed-message work; source order was verified at review.

The runtime restricts MLS application envelopes to text and attachments; group controls require a pinned bilateral Signal channel. Native MLS checks credential/signing-key equality, the expected Welcome signer, coordinator authorization and the exact approved future membership before merging a commit. These are source-review observations, not a substitute for compiled tests or an independent audit.

The native owner subsequently implemented per-connection cancellation for active writers and wiping of partially copied Java MLS result fields on bridge decoding failures. Root integrated encrypted guard-history checkpoints before clearing the live Arti state directory. These fixes remain subject to compiled regression and device validation; process termination, active plaintext Arti metadata, checkpoint lag and native-memory limits still apply.
