# Messaging runtime API

`MessagingEngine(crypto, db, identity, session, directory: Path, scope: CoroutineScope, mutex: Mutex, onChanged: () -> Unit, onError: (String) -> Unit)` belongs to one unlocked vault.

`fetchPeerBundle` is the one **suspending** public action and the one that must **not** be called with the mutex held — see "Pairing key-bundle fetch" below. Synchronous public actions assume the caller **already holds the supplied mutex** on IO: `sendText(chatId, text, forwarded: Boolean = false)`, `sendAttachment(chatId, name, mime, bytes, forwarded: Boolean = false): String`, `createGroup(name, members): String`, `removeMember(groupId, member)`, `leaveGroup(groupId)`, `syncEvidence(peer)` and `decryptAttachment(fileId): Pair<FileRecord, ByteArray>`. `start()` starts incoming/outbox workers. `close()` cancels workers before identity/session close and schedules bounded closure of every tracked stream; the controller still shuts down the transport process. Public actions only encrypt and persist; network writes happen after releasing the mutex. `onChanged` executes under the mutex and may synchronously query SQLCipher.

### Pairing key-bundle fetch (2026-09-17, T4.16)

QR format 2 keeps the ~1832-byte PQXDH bundle out of the pairing QR and carries only its SHA-256 hash, so the bundle is fetched over the peer's onion. Two envelopes carry it — `Envelope.BundleRequest(nonce)` and `Envelope.BundleResponse(nonce, bundle)`, `EnvelopeCodec` wire version 3 — inside the new `PacketKind.BUNDLE`. That kind is the only one whose payload is **plaintext rather than ciphertext**, because it is exchanged before any Signal session exists; nothing secret may ever be put in it, and its integrity rests entirely on the hash the peer signed into the QR, not on the transport.

`attachPairingBundles(source: ((ByteArray) -> ByteArray?)?)` installs the answer source — `NoMessagesController` wires it to `PairingEngine.bundleFor`. It is invoked from `accept`, i.e. already under the controller's mutex, which is the only lock the pairing engine is mutated under. Null (no pairing screen open) means every incoming request is answered with silence.

`transportAttached: Boolean` reports whether a reachable transport has been published, so the controller can show "waiting for Tor" instead of failing a fetch that has no network to run on.

`fetchPeerBundle(onion: String, nonce: ByteArray, timeoutMillis: Long): ByteArray` opens a stream to `onion`, sends the request and returns the raw encoded bundle. **It is deliberately not an `atomic`/mutex-holding action.** While it suspends, the peer is running the mirror-image fetch against this device, and answering that needs the very same mutex; holding the lock across a 5–40 s circuit build would deadlock two devices that scanned each other. The caller verifies the result (`PairingEngine.acceptPeerBundle`) and wipes the returned buffer — nothing here grants it any trust.

Routing: streams opened by `fetchPeerBundle` are registered in `bundleWaiters` by connection id, and `receiveLoop` hands the assembled wire straight to the waiter instead of to `accept` — a `BundleResponse` belongs to no Signal session, so `accept` would have nothing to authenticate it against.

On the answering side, a `PacketKind.BUNDLE` packet is handled **before** the receipt cache and before the `atomic { }` vault transaction: it touches no database row, no ratchet and no identity export. It is the one packet an unpaired stranger may legitimately send. The payload ceiling is 8 KiB. An unknown, stale or already-consumed nonce is answered with **silence, not an error envelope** — an error would confirm to a bare nonce probe that this onion is running a pairing screen. Admission uses `MessagingBundleLimiter`, a separate 1/s-sustained, burst-4 token bucket: these requests arrive before any session exists, so `MessagingTrialLimiter`'s "is this a peer we already know" shortcut does not apply to them, and one shared bucket would let a pairing flood starve ordinary message admission. That bucket only bounds decoder work; the real defence is structural and lives in `PairingEngine.bundleFor` — a nonce this device minted, inside its own window, answered exactly once.

Neither envelope is ever queued into a Signal lane. Reaching `handle()` with one means a paired peer wrapped it in its ratchet, which no honest build does, and it is rejected there.

### Doorbell knock (2026-09-18, T4.17)

A contact whose vault is locked is unreachable on its messaging onion but still answers on its **doorbell** onion (see [native-api.md](native-api.md), "Doorbell"). The engine uses that to wake a peer it cannot deliver to, and nothing else: a knock carries no content, no identity and no session material.

**When it fires.** Every delivery failure in `outboxLoop` is a candidate — not just a connect refusal, because from here a stream that never answered and a stream that was refused are the same event. `ringDoorbell(peer)` is called with the contact id, and the attempt is admitted only if the contact actually has a doorbell agreed with this device: `contacts.doorbell_onion` non-empty **and** `contacts.doorbell_token` exactly 32 bytes (`DoorbellKnockPolicy.TOKEN_BYTES`). A contact paired before T4.17 has neither, which is not an error — it simply has no doorbell, and it is skipped in silence.

**Which token.** `contacts.doorbell_token`, the secret **that peer** minted in its own signed offer and expects to be presented at its doorbell. Never `doorbell_token_issued`, which is this device's own and is only ever loaded into the local verifier at lock. The token is copied under the mutex, handed to `TorConnection.doorbellKnock` and wiped in a `finally`; the frame itself is built natively and the token never crosses back.

**Cost, and why it is asynchronous.** One knock costs the native side up to **240 s** — 180 s of bootstrap plus a 60 s exchange — and there is no retry of its own, because that budget already covers a full circuit build. It therefore runs fire-and-forget on the engine scope rather than inside the outbox worker that observed the failure: the outbox admits four workers at a time and at most one per peer, so waiting for a knock there would stall that contact's entire queue for four minutes, including the very retry the knock exists to make succeed. Exactly one knock is in flight per contact, held in a `ConcurrentHashMap` keyed by contact id; the job is registered before it runs (`CoroutineStart.LAZY`), so two failures landing at the same instant cannot both pass the "already knocking?" test — the loser cancels a job that never executed a line. No error escapes: an unreachable doorbell is an ordinary outcome, not a fault.

**The schedule.** `DoorbellKnockPolicy` is the pure decision, in the same spirit as `MessagingPolicy` and `TransportSupervisor`: no Android, no database, no Tor, no wall clock, no coroutine — `now` is a parameter, so floor, growth and ceiling are all exercised by JVM unit tests with no mocks and no sleeps. The interval is **10 / 20 / 40 / 80 / 120 minutes**. The first step is the floor the feature requires (at most one knock per contact per 10 minutes) and is also what an **acknowledged** knock returns to, since a peer that answered can be woken cheaply again. The doubling covers the case the doorbell exists for, a device that has been off for hours, and it stops at two hours so an unattended sender still wakes a peer that comes back the next morning within one ceiling instead of converging on a delay longer than the outage. The floor exists because the outbox retries a queued frame every 30 s: without a schedule of its own, one unreachable contact would produce a knock per retry.

**The record.** `opaque_blobs` namespace `doorbell_knocks`, key = `ContactRecord.id` (the contact's `id_pub`, stable across sessions), value = **12 bytes**: a big-endian `long` of epoch millis plus a big-endian `int` failure count. The stamp is written **when a knock is dispatched, not when it succeeds** — recording the attempt is what makes the rate limit hold in the common case, a peer that is off and whose doorbell is therefore just as unreachable as its messaging onion; stamping on success only would turn every outbox retry into a fresh 240 s knock. The failure counter only ever stretches the interval and saturates rather than overflowing. It resets on any sign of life: an acknowledged knock, a delivered message or a received ACK from that contact. A knock that failed while **this** device's own transport was dying does not stretch the peer's schedule, since it says nothing about the peer — but the attempt stamp stays, so a local outage still cannot produce a knock storm. A row of any other length decodes to `null`, which means "never knocked" and therefore *eligible*: a corrupt schedule must not be able to silence the doorbell permanently. A stamp in the future is likewise treated as eligible rather than as a very long wait — the clock moved backwards (NTP, timezone, a restored vault), and it costs at most one extra knock because dispatching rewrites the stamp.

### Transport attachment and outbox pause

The engine does not own the transport. `attachTransport(connection: TorConnection?)` is called by `NoMessagesController`: with the live `TorConnection` once its onion descriptor is published (`NetworkStatus.ONLINE`), and with `null` whenever the controller tears a failed or dead one down. There is no transport at `start()`.

While it is `null`, sending is **paused, never failed**: the outbox worker parks in 500 ms ticks without querying the ready set, so a queued envelope keeps its position and does not burn its thirty-second per-item cooldown or rewrite its `attempts` row against an unreachable network; the receive worker parks in 200 ms ticks, and stream closing becomes a no-op. Messages composed offline simply accumulate as `PENDING`, which is the same durable state they already had between attempts.

One transport is one child process: `TorService` refuses a second START, so every reconnection attempt builds a new `TorConnection` and the controller attaches it. A worker therefore reads the field once per tick instead of capturing it, and a channel closed by a dying child parks the receive loop instead of ending it.

Closing a stream is best effort and never propagates. Every stream teardown (`closeStream`, the expiry sweeper and `close()`) goes through a single guarded call: the `:tor` child can die at any instant, and a `DeadObjectException` escaping a teardown would kill the receive, outbox or sweeper loop permanently — leaving an engine that no longer reads the healthy replacement transport the supervisor attaches next. Only genuine cancellation (the lock) passes through.

Signal identity state, MLS state, message, recipient-specific outbox, accepted ciphertext receipt and cached encrypted ACK persist atomically before transmission. Failed SQL transactions restore `PairingIdentity` in place. Group application messages are one MLS ciphertext fanned out to recipients. Control messages use paired Signal channels. Group creation may remain pending until all invited paired peers provide fresh request-bound MLS key packages. A pending group cannot send applications.

Attachments are at most 8 MiB; the encrypted envelope contains the file ciphertext and fresh file key. Local objects use authenticated 64 KiB chunks and a key wrapped with the unlocked vault FBK. `decryptAttachment` returns verified bytes for an in-app memory viewer only; caller owns and wipes returned bytes. Every caller is in `NoMessagesController`: `openAttachment`, the four inline media loaders (`loadAudioPreview`, `loadAudioBytes`, `loadImagePreview`, `loadVideoPreview`) and `forwardMessage`. None of them writes the returned plaintext anywhere — received attachments have no save, share, chooser, `FileProvider` or `MediaStore` path out of the app at all. See `docs/security-model.md` and `SPEC.md` §9.3.

### Forwarding (2026-09-17, T4.12)

`sendText` and `sendAttachment` take an optional trailing `forwarded: Boolean = false`. The default preserves every existing call site: an ordinary compose-and-send is unchanged. When `true`, the value is written into the `Envelope.Text`/`Envelope.Attachment` it builds (wire version 2 — see [message-api.md](message-api.md)) and into the persisted `MessageRecord.forwarded` column, on both the sending and the receiving side, so the flag survives a relock without re-decoding the envelope body. `MessagingEngine.envelopeForwarded` is the single place that maps an envelope to that column, and it yields `false` for every control type.

Forwarding is a normal send, not a separate path: the new envelope goes through `sendApplication` into the same durable outbox, so it inherits lane ordering, the ACK deadline and — most importantly — the transport pause above. With no transport attached, forwarded copies accumulate as `PENDING` exactly like any other composed message; no extra pause handling exists for them.

`NoMessagesController.forwardMessage(messageId: String, targetChatIds: List<String>)` is the caller. It de-duplicates and drops blank target ids, returns silently when the resulting list is empty or the message id is unknown, and decodes the stored row's envelope (wiping the stored body buffer in a `finally`). A `Text` is re-sent per target with `forwarded = shouldMarkForwarded(record.peerOrGroup, target)`. An `Attachment` cannot be relayed from stored history — `MessagingEngine.history` keeps attachment rows with an empty ciphertext and a zeroed file key — so the bytes are fetched through `decryptAttachment(fileId)`, re-sent to each target with `sendAttachment(..., forwarded = shouldMarkForwarded(record.peerOrGroup, target))`, and the plaintext buffer is wiped in a `finally`. Each destination therefore receives a brand-new envelope with a fresh message id, timestamp, file key and file id, since the attachment is re-encrypted from plaintext rather than relayed as stored ciphertext. Any other envelope type reaching this method is ignored rather than reported. Eligible destinations come from `UiState.forwardTargets`, assembled by the controller as paired non-`displayOnly` contacts plus groups whose status is `READY`.

The flag is decided **per destination**, not per forward: `shouldMarkForwarded(sourceChatId: String, targetChatId: String): Boolean` in `ui/UiLogic.kt` (`internal`, same `app` module, already reachable through the controller's `import dev.mx3.nomessages.ui.*`) returns `sourceChatId != targetChatId`. The source chat is `MessageRecord.peerOrGroup` — the conversation the original row lives in. Resending a message into the very chat it already belongs to is indistinguishable from typing it again, so that copy goes out as an ordinary message with `forwarded = false` and no "Forwarded" label; only a copy that crosses into a different conversation carries the bit. The picker deliberately still offers the source chat as a destination — the rule suppresses the label, it does not remove the capability — so one confirm that selects the source chat plus two other contacts produces one unlabelled copy and two labelled ones. Nothing about the wire format (envelope v2) or the `messages.forwarded` column changed; only the value computed at send time. Covered by `UiLogicTest`: `resending into the source chat is not labelled as forwarded` and `forwarding into a different chat is labelled as forwarded`.

`FileRecord.id` is lowercase hex of the envelope's 16-byte file ID. Its `encryptedParameters` is `crypto.seal(FBK, fileKey, idHex.UTF8)`. History attachments encode the normal envelope with empty ciphertext and a zeroed key; their authenticated key and ciphertext live in the file record/object. The transfer accepts up to 8 MiB plaintext and the codec reserves 64 KiB for file-format overhead.

Creation is limited to 3..100 members. Existing groups may shrink to 1 member. MLS forbids a committer from removing itself: coordinator leave sends an authenticated `GroupLeave` to every survivor, transferring coordination to the lexicographically first surviving identity. That identity issues the removal Commit after accepting the transfer. Recipients retry a Commit that arrives before the transfer. The leaving device durably queues the transfer and clears its local MLS state. Removal sends no new-epoch Commit to the removed member. A remote removal becomes visible through successful membership updates on surviving devices; the removed device cannot receive the new epoch.

Workers limit concurrent outbound attempts to four distinct destinations. Each durable destination/lane queue sends its next envelope only after an authenticated ACK for the previous one. Lanes separate direct chats, each MLS group (applications plus membership controls), key-package request nonces, and evidence, so quota rejection in one group cannot block unrelated chats. A completed write has a sixty-second ACK deadline; expired, rejected, completed, and closing-engine streams are explicitly closed. At most sixteen assemblies share a 32 MiB budget; a timed receive loop clears incomplete assemblies after sixty seconds without input.

Unknown Signal streams use parse-once candidate decryption, direct pinned-identity routing for PreKey messages, and recently authenticated peers first. Regular messages attempt at most 64 peers at <=64 KiB or 8 peers above that size. Failed exact ciphertext hashes resume their candidate cursor on retransmission. Every retry refreshes the eligible set: newly paired peers and newly joined groups are tried first, while prior unscanned candidates retain their rotation; a change in recency ordering alone cannot restart the scan. The cache retains no ciphertext, has at most sixteen entries with a conservative 24 MiB metadata budget (the current 1024-contact limit puts it below approximately 4 MiB), and expires after 120 seconds idle for small messages or fifteen minutes for large transfers. All unknown Signal/MLS packet invocations use a global two-per-second token bucket with burst four. Replies on a locally opened stream authenticate against its expected peer directly. With many contacts, a first regular message can require multiple thirty-second retries; this bounds work and does not promise denial-of-service immunity. MLS uses the same 64/8 bounded and resumable work slices over at most 128 active groups, loading one secret snapshot at a time.

Outbox payloads are deduplicated by the storage adapter; ACKs remove recipient rows and release the shared payload only after its last recipient. SENT means flushed to Tor; DELIVERED requires authenticated ACKs from all intended recipients. Native MLS retains exactly two prior epochs: cross-sender application messages delayed beyond two membership changes, or sent by a now-removed member, can remain undeliverable. Per-group destination FIFO cannot establish global ordering between different senders; this remains a device integration/release gate.

Group clique evidence is fetched only for the selected members. Incoming evidence is admitted only when both endpoints are already paired locally; the store is capped at 16,384 edges. Synchronization uses at most 256 proofs per envelope. New evidence gossip persists as a durable work item, then encrypts at most four recipients per worker tick, rather than generating unbounded recipient outbox writes in the receiving transaction. Invite/Commit proof imports do not re-gossip the full clique. Active group admission and receive enumeration share the 128-group cap; inactive records do not consume it.

Unused one-time MLS key packages expire after 24 hours, are pruned before new requests, and are rejected/removed at Welcome admission if expired. There are at most four outstanding packages per paired requester and 128 globally. A Welcome delayed past package reclamation cannot join; group coordination requires overlapping availability within this resource window.

Attachment objects are flushed and atomically renamed, and the parent media directory is synchronized before the SQL transaction commits its file reference. If a process dies between rename and commit, an authenticated retransmission adopts the existing unreferenced object only when its bounded ciphertext matches byte-for-byte. Referenced files and allocation cover are never overwritten or swept by this recovery path.

Permanent control prerequisite failures use encrypted `Envelope.ControlRejected`; its `requestId` is the original envelope ID, not a key-package nonce. Rejections use four bounded reasons, persist with the incoming ratchet state and receipt cache, and enter a durable rejection lane. The sender only honors a rejection for that peer's outstanding rejectable control, removes that control without claiming delivery, records `failed_controls`, and stores `group_error` as `peerId:REASON`. It ACKs the rejection itself. Group application sends stop while a group error exists; removing the failed member clears the associated error. `leaveGroup` cancels a pending creation and its controls, freeing the local active-group slot. Coordinator-transfer ordering and storage/transport failures remain retryable.

Regression checks: `python3 app/src/test/python/test_messaging_queue.py` executes the production readiness SQL against SQLite and covers quota head-of-line blocking, same-group epoch ordering, destination isolation, and fairness after an offline attempt. `MessagingPolicyTest` covers the shared Signal/MLS token bucket, large-packet work bounds, cursor refresh after late Welcome/pairing and recency changes, package quotas, and control lanes in the Android JVM test suite.
